# 0001. Vision grounding with LFM2.5-VL on a CPU

- Date: 2026-11-20
- Status: done
- Confidence: measured (one machine, one synthetic image, 8 targets; small sample)
- Decisions informed: [ADR 0004](../adr/0004-local-first-provider-agnostic-models.md), [ADR 0005](../adr/0005-ui-automation-first-pointing.md)

## Question

Can LFM2.5-VL-1.6B, running locally on a CPU with no GPU, return click-accurate coordinates for a named UI element in a screenshot, fast enough for an interactive buddy?

## Hypothesis

Written after the first runs, so treat as informal: we expected a 1.6B model to be coarse at pixel coordinates but usable with normalised boxes, and CPU latency of several seconds. The exact numbers were unknown beforehand.

## Setup

- Machine: Intel i7-10750H (6 cores / 12 threads), 15.8 GB RAM, Windows 11, no GPU used.
- Runtime: llama.cpp `b12549`, `llama-server`, `win-cpu-x64` build (multiple CPU backends present, so AVX2 kernels were available).
- Model: `LiquidAI/LFM2.5-VL-1.6B-GGUF`, `Q4_K_M` (731 MB) with `mmproj-LFM2.5-VL-1.6b-Q8_0` (583 MB).
- Server flags: `-t 6 -c 4096`, temperature 0, `max_tokens` 40.
- Test image: synthetic 1280x720 UI with 8 labelled buttons (220x70 px) at irregular positions, generated by [`make-test-image.ps1`](../../spikes/vision-grounding/make-test-image.ps1). Ground-truth centres are in the data file.
- Scoring: a **hit** is a predicted centre inside the button rectangle. Error is the Euclidean distance in pixels to the true centre. Scorer: [`benchmark.mjs`](../../spikes/vision-grounding/benchmark.mjs).
- Prompts (variant name: what the model was asked for):
  - `pixel`: centre as `[POINT:x,y]` in pixels, image size stated in the prompt.
  - `normalized`: centre as fractions 0 to 1.
  - `bbox`: bounding box `[x1,y1,x2,y2]` as fractions 0 to 1.

## Method

1. Generate the image and ground truth.
2. Start `llama-server` with the model and projector.
3. For each of 8 labels, send the image and a prompt, parse the reply, score it.
4. Repeat for each prompt variant, then for a 640x360 downscale of the same image.
5. Vary threads and micro-batch size on a single query to look for latency wins.

## Results

| Prompt | Image sent | Hits | Mean error | Mean latency (new image) |
|---|---|---|---|---|
| `pixel` | 1280x720 | 0/8 | 287 px | 23.3 s |
| `normalized` | 1280x720 | 1/8 | 203 px | 23.7 s |
| `bbox` | 1280x720 | 4/8 | 66 px | 24.2 s |
| `bbox` | 640x360 | 3/8 | 109 px | 7.6 s |

Raw per-target replies: [`data/0001-vision-grounding-runs.json`](data/0001-vision-grounding-runs.json).

Latency details:

- 1280x720 became 810 prompt tokens; 640x360 became 263.
- Prompt processing ran at about 35 tokens/s; generation at about 30 tokens/s. Image processing dominates.
- Threads 6, 8 and 12 and micro-batch 512 vs 1024 changed latency by under 15%.
- An identical repeat request took 0.7 s because of the prompt cache. Real screenshots are different every time, so this does not help.

## Analysis

- Asking for pixel coordinates failed completely: the model repeated the same few points (for example `[POINT:560,320]` for four different buttons), which looks like a learned default rather than perception.
- Normalised boxes were the only usable format. Even so, values clustered on 0.05 steps and the same box was sometimes returned for different labels, so the model is placing things coarsely by region, not by pixel.
- Halving the image width cut latency by about 3x and cost about one hit; the quality drop is within the noise of an 8-target test.
- We would **not** conclude that LFM2.5-VL cannot ground at all: the sample is small, the synthetic UI is simple, and we did not test larger images, other quantizations, the 450M variant, or other prompt formats.

## Conclusion

On a CPU-only laptop, LFM2.5-VL-1.6B cannot give click-accurate pointing and takes 8 to 24 s per new image. Pointing must come from another source (Windows UI Automation), with the model choosing among listed elements.

## Eval potential

Good candidate for a regression eval:

- Inputs: generated images plus target labels (extend with real app screenshots and hand-labelled boxes).
- Expected output: a box or element id.
- Scoring: hit rate and median error in pixels; latency measured separately.
- Suggested thresholds: hit rate at least 90% for the UIA-assisted element-selection variant (see ADR 0005); report, but do not gate on, raw-box hit rate.
- Next step for evals: add `--out` JSON output to the harness and a fixed seed for positions.

## Reproduce

```bash
powershell -File spikes/vision-grounding/make-test-image.ps1 -OutDir ./data
llama-server -m LFM2.5-VL-1.6B-Q4_K_M.gguf --mmproj mmproj-LFM2.5-VL-1.6b-Q8_0.gguf -t 6 -c 4096 --port 8089
node spikes/vision-grounding/benchmark.mjs data/synthetic-ui.png data/synthetic-ui.json http://127.0.0.1:8089 bbox
```
