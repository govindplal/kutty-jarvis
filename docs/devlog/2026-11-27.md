# Devlog 2026-11-27

## Speech voice licence review

- **Question.** Can a free MIT app use or ship the Piper Lessac voices? Finding 0002 had flagged this as unresolved.
- **Surprise.** The Blizzard 2013 Lessac dataset is licensed for research only: no commercial use, no redistribution, licence granted to a named person. Piper's own licensing page says the same and takes no position on whether trained weights are derivatives. Several other popular voices (hfc_male, kusal, libritts_r) are fine-tuned from lessac and inherit the problem.
- **Second surprise.** The "MIT" Piper binary is not clean either: it links espeak-ng (GPL-3.0), and the maintained successor is GPL-3.0 and ships Python wheels, not an exe. A separate process keeps our code MIT; downloading on first run keeps GPL binaries out of our installer.
- **Outcome.** Proposed default is `en_US-ljspeech-medium` (public domain, from scratch, 63.5 MB) on the pinned 2023.11.14-2 binary, both downloaded on first run. Written up in [research 0002](../research/0002-speech-voice-licences.md) with a dated amendment to [ADR 0007](../adr/0007-speech-stack.md).
- **Not done.** No audio was generated: ljspeech on the old binary, its speed and its sound are unverified. Not legal advice.

## Debug export of the last recording, and a speech test kit

- **Why.** Speech recognition has only been tested on synthetic speech. To test real microphone audio we need the WAV on disk, but ADR 0010 says recordings stay in memory.
- **Built.** Debug builds (`debug_assertions`) write each finished recording to `%TEMP%/kutty-jarvis/last-recording.wav`, overwriting the previous one. In release builds the export function is a stub with no file access, so audio can never be written. The path travels in the `recording-finished` payload as an optional `debugWavPath` and is shown in the window only when present. ADR 0010 has a dated amendment.
- **Tests.** Rust: the export keeps exactly one file and overwrites it (debug); `release_builds_never_export_audio` passes under `cargo test --release`. Vitest: the path appears only when present.
- **Kit.** `spikes/speech-latency/mic-test.md` has eight buddy questions and the steps; `transcribe-wav.mjs` transcribes a WAV with LFM3-Audio and prints transcript, latency and WER. One check on `s01.wav`: transcript matched the reference exactly (WER 0%), 1.4 s for 3.6 s of audio. That is a script check, not a benchmark. [Finding 0005](../findings/0005-real-microphone-speech-recognition.md) is open until the owner records.
- **What did not work.** The end-to-end check in the running app failed to start for two reasons. First, Ctrl+Alt+Space was already registered by another process, so the app panicked at start-up ("HotKey already registered"); the only likely candidate was the Claude desktop app, not confirmed. Second, a temporary build on Ctrl+Alt+F9 (reverted, not committed) started fine, but simulated key holds produced no push-to-talk event and no file, although `GetAsyncKeyState` saw the keys down. So the file export has not been seen in the running app. Cause not found.

## Push-to-talk shortcut conflict (fix/hotkey-conflict-non-fatal)

- **Symptom.** Starting the app while another program held Ctrl+Alt+Space crashed it at start-up ("HotKey already registered"). Registration errors were returned from `setup`, which aborts Tauri.
- **Fix.** `hotkey::register` now logs the failure and records a `ShortcutStatus` (label, registered, notice) in managed state. The window reads it through the `push_to_talk_status` command (an event sent during setup would fire before the page listens). The tray tooltip is updated too.
- **Override.** `KJ_PUSH_TO_TALK` is parsed by the plugin's `Shortcut::from_str`; invalid values fall back to the default with a visible notice. See the 2026-11-27 note in [ADR 0008](../adr/0008-tray-app-and-push-to-talk-hotkey.md).
- **Suspect.** The Claude desktop app probably owns Ctrl+Alt+Space on the owner's machine (unconfirmed).

## Pointing: UI Automation list and cursor overlay

- **Built** the pointing half of the buddy: a `uia` module that lists the foreground window's visible elements as a numbered prompt (`12 button "Save" (x,y,w,h)`), and a transparent, click-through overlay window that flies a cursor to an element and rings it ([ADR 0013](../adr/0013-pointing-overlay-second-tauri-window.md)). Debug builds get a small panel and two commands to try it by hand. No model is called yet; the model loop will pick an element number (ADR 0005).
- **Measured** across Notepad, File Explorer, Edge, VS Code and our own window ([finding 0007](../findings/0007-uia-enumeration-across-apps.md)): every list in under 0.2 s, and the cursor landed at the exact centre of all 15 targets at 125% scale.

### Things that went wrong (useful for the blog)

1. **Real apps are noisy in app-specific ways.** Explorer's details view lists every cell of every row as an `edit` named after its column; VS Code names icons with private-use glyphs and nests a full file path group inside each tab. Both blew the 150 cap on the first try. Two small rules (fold item parts into the item, ignore icon glyphs) fixed both.
2. **Our overlay hid our own window from UI Automation.** While the full-screen overlay was up, our main window's tree dropped from 19 elements to 3. Other apps were unaffected. Lesson: list first, then point.
3. **Chromium builds its accessibility tree lazily.** The first listing of a fresh VS Code window had 4 elements, the second had 166.
4. **We could not move focus or take screenshots.** The sandbox blocked simulated key presses and screen-capture helpers, so the test could not bring each app to the front. Fix: a debug option to list a given process's main window, and accuracy checked from the overlay's own drawn state over the WebView2 debug port. A human still needs to watch it once.
5. **A "temporary" Edge profile signed itself in.** Edge silently signed the throwaway test profile into the Windows account and started syncing. The sanitiser caught the account email in the raw data before it reached the repo. Lesson: scrub raw accessibility dumps; they contain whatever is on screen.
6. **The hotkey was already taken** by another app on this machine, which made the app fail at start-up. Worked around locally for the test; a separate change makes it non-fatal.

## Model loop: spoken question in, answer and pointing out (feat/model-loop)

- **Built** the missing middle of the buddy ([ADR 0012](../adr/0012-model-loop-llama-server-sidecar.md)): on key release the app transcribes the recording with LFM3-Audio, asks LFM2.5-VL with the screenshot, the transcript and the numbered element list, strips a `[POINT:n]` tag from the reply, validates it against the list and flies the overlay there. Both models run as lazily started `llama-server` sidecars; the pipeline sits behind two traits so a cloud provider can replace either one. Setup steps: [local-models.md](../setup/local-models.md).
- **Measured** on a 2-vCPU Linux sandbox (llama.cpp b12549, CPU only, so slower than the owner's laptop); numbers are in the PR.

### Things that surprised us

1. **The screenshot dominates latency.** With a 1280 px frame the vision answer took about 33 s; at 960 px about 13 s, at 640 px about 12 s. Pointing comes from the element list, so the local client now shrinks the frame to 960 px (`KJ_VLM_IMAGE_EDGE`).
2. **Rules alone did not work for the 1.6B model.** With only instructions it answered with just `[POINT:2]`, or repeated the whole element list. Two short worked examples in the system prompt fixed the format. It still sometimes points at the wrong element for open questions ("what is this program about?"), so the parser only trusts ids that exist and the spoken text never depends on the tag.
3. **Test speech is not real speech.** espeak-ng's "gear icon" was heard as "bear icon"; that says more about the synthetic voice than the model, and finding 0005 (real microphone) is still open.

## Speech output: Piper with a SAPI fallback (feat/speech-output-piper)

- Added `tts::speak` and `tts::stop` for the model loop (ADR 0014). Piper runs as a child process; Windows SAPI speaks while Piper is not installed. One utterance at a time, and a new hotkey press can cut speech off.
- Decision: download the engine and voice (about 90 MB) on the first spoken reply, not at install, and use SAPI meanwhile. Rationale and the alternatives are in the ADR.
- Pinned SHA-256 for every file. Cross-check: the voice model matches the Hugging Face LFS id, the two small voice files match the git blob ids from the HF tree API; the engine archives were hashed after download.
- Measured on Linux (2 CPU, gVisor, Piper linux x86_64 build): download and verify of 4 files took 5.2 s; synthesising a 4.7 s sentence took 1.75 s including process start and model load. No sound card, so playback was not heard. SAPI and cpal playback are only compile-checked for Windows.
- Surprise: the `windows` crate maps `ISpVoice::WaitUntilDone` to `Result<()>`, so its S_FALSE timeout looks like success. A loop built on it would stop immediately; the code polls `GetStatus` instead.
- Surprise: adding `ureq` with rustls pulls in `ring`, which needs a C compiler and Windows headers, so the local cross-target clippy cannot build it here; CI on Windows does.
