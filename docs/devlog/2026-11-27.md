# Devlog 2026-11-27

## Speech voice licence review

- **Question.** Can a free MIT app use or ship the Piper Lessac voices? Finding 0002 had flagged this as unresolved.
- **Surprise.** The Blizzard 2013 Lessac dataset is licensed for research only: no commercial use, no redistribution, licence granted to a named person. Piper's own licensing page says the same and takes no position on whether trained weights are derivatives. Several other popular voices (hfc_male, kusal, libritts_r) are fine-tuned from lessac and inherit the problem.
- **Second surprise.** The "MIT" Piper binary is not clean either: it links espeak-ng (GPL-3.0), and the maintained successor is GPL-3.0 and ships Python wheels, not an exe. A separate process keeps our code MIT; downloading on first run keeps GPL binaries out of our installer.
- **Outcome.** Proposed default is `en_US-ljspeech-medium` (public domain, from scratch, 63.5 MB) on the pinned 2023.11.14-2 binary, both downloaded on first run. Written up in [research 0002](../research/0002-speech-voice-licences.md) with a dated amendment to [ADR 0007](../adr/0007-speech-stack.md).
- **Not done.** No audio was generated: ljspeech on the old binary, its speed and its sound are unverified. Not legal advice.

## Debug export of the last recording, and a speech test kit

- **Why.** Speech recognition has only been tested on synthetic speech. To test real microphone audio we need the WAV on disk, but ADR 0010 says recordings stay in memory.
- **Built.** Debug builds (`debug_assertions`) write each finished recording to `%TEMP%/kutty-jarvis/last-recording.wav`, overwriting the previous one. In release builds the export function is a stub with no file access, so audio can never be written. The path travels in the `recording-finished` payload as an optional `debugWavPath` and is shown in the window only when present. ADR 0010 has a dated amendment.
- **Tests.** Rust: the export keeps exactly one file and overwrites it (debug); `release_builds_never_export_audio` passes under `cargo test --release`. Vitest: the path appears only when present.
- **Kit.** `spikes/speech-latency/mic-test.md` has eight buddy questions and the steps; `transcribe-wav.mjs` transcribes a WAV with LFM3-Audio and prints transcript, latency and WER. One check on `s01.wav`: transcript matched the reference exactly (WER 0%), 1.4 s for 3.6 s of audio. That is a script check, not a benchmark. [Finding 0005](../findings/0005-real-microphone-speech-recognition.md) is open until the owner records.
- **What did not work.** The end-to-end check in the running app failed to start for two reasons. First, Ctrl+Alt+Space was already registered by another process, so the app panicked at start-up ("HotKey already registered"); the only likely candidate was the Claude desktop app, not confirmed. Second, a temporary build on Ctrl+Alt+F9 (reverted, not committed) started fine, but simulated key holds produced no push-to-talk event and no file, although `GetAsyncKeyState` saw the keys down. So the file export has not been seen in the running app. Cause not found.

## Push-to-talk shortcut conflict (fix/hotkey-conflict-non-fatal)

- **Symptom.** Starting the app while another program held Ctrl+Alt+Space crashed it at start-up ("HotKey already registered"). Registration errors were returned from `setup`, which aborts Tauri.
- **Fix.** `hotkey::register` now logs the failure and records a `ShortcutStatus` (label, registered, notice) in managed state. The window reads it through the `push_to_talk_status` command (an event sent during setup would fire before the page listens). The tray tooltip is updated too.
- **Override.** `KJ_PUSH_TO_TALK` is parsed by the plugin's `Shortcut::from_str`; invalid values fall back to the default with a visible notice. See the 2026-11-27 note in [ADR 0008](../adr/0008-tray-app-and-push-to-talk-hotkey.md).
- **Suspect.** The Claude desktop app probably owns Ctrl+Alt+Space on the owner's machine (unconfirmed).
